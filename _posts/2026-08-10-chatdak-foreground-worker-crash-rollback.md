## 오늘 한 일

- 다른 앱으로 전환하면 AI 정리 작업이 끊기고 처음부터 재시작되는 문제를 발견
- `CoroutineWorker`를 포그라운드로 승격시켜 고치려다가 앱이 통째로 죽는 크래시를 만남
- Android 12+ 의 백그라운드 실행 제약이 원인이라는 걸 확인하고 되돌림

## 핵심 작업 해설

### 문제: 다른 앱으로 전환하면 처리가 처음부터 다시 시작된다

실기기에서 AI 정리를 반복 테스트하던 중, 처리가 도는 동안 다른 앱(SNS)으로 전환했더니 시스템 로그에 이런 게 반복해서 찍혔다.

```
WorkerStoppedException
"rescheduling for later execution"
```

AI 요약 호출은 20초에서 3분까지 걸리는 무거운 작업인데(응답이 느린 모델일수록 오래 걸린다), 그 사이 다른 앱이 포그라운드를 가져가면 시스템이 백그라운드 작업을 강제로 끊고 재스케줄한다. 문제는 **재스케줄된 작업이 이전 진행 상황을 이어받지 않고 처음부터 다시 시작**한다는 것이었다. 외부 API 호출이 매번 새로 나가니 시간과 비용이 그대로 낭비됐다.

### 시도한 해결책: 포그라운드로 승격

`CoroutineWorker`는 `setForeground()`를 호출해서 스스로를 포그라운드 서비스처럼 보호받게 만들 수 있다. AI 정리 중에는 이걸 호출해서 시스템이 함부로 끊지 못하게 하려고 했다.

```kotlin
override suspend fun doWork(): Result {
    setForeground(
        ForegroundInfo(
            NOTIFICATION_ID,
            buildProcessingNotification(),
        )
    )
    // ... 실제 처리 ...
}
```

새 알림 채널과 `FOREGROUND_SERVICE_DATA_SYNC` 권한도 추가했다.

### 그런데 이 해결책 자체가 앱을 크래시시켰다

빌드해서 실기기에 올리고 다시 테스트했더니, 이번엔 처리가 끊기는 정도가 아니라 **앱 전체가 죽었다.**

```
java.lang.RuntimeException: Unable to start service
androidx.work.impl.foreground.SystemForegroundService ... ACTION_START_FOREGROUND
```

원인은 **Android 12 이상에서는 앱이 이미 포그라운드 상태가 아니면 `startForegroundService()` 자체를 시스템이 막는다**는 제약이었다. 그런데 정작 이 문제가 터지는 상황이 바로 "앱이 백그라운드에 있는 동안 `JobScheduler`가 워커를 (재)실행하는" 그 시점이다 — 포그라운드로 승격하고 싶어서 부른 코드가, 하필 포그라운드가 아닐 때만 실행돼서 그대로 예외를 던진 것이다.

더 골치 아팠던 건, 워커의 코드 전체를 `runCatching {}`으로 감싸도 이 예외를 못 잡는다는 점이었다. 이 예외는 워커의 코루틴 내부가 아니라, **OS가 앱 프로세스의 메인 스레드에서 실제 서비스를 띄우려다가 던지는** 것이라 워커 쪽 예외 처리 범위 바깥에서 발생한다.

### 되돌림

`setForeground()` 호출, 새로 추가한 알림 채널, `FOREGROUND_SERVICE_DATA_SYNC` 권한을 전부 제거했다. 원래 있던 문제(다른 앱 전환 시 처리가 끊기고 재시작되는 것)는 남았지만, WorkManager 자체의 재시도 메커니즘이 결국은 성공시킨다는 걸 확인했다 — 같은 작업이 여러 번 끊겼다 붙었다 하면서도 끝내 완료됐다(약 10분 걸려 재시도만으로 마무리). **느리고 API 비용은 낭비되지만, 크래시로 앱이 죽는 것보다는 훨씬 낫다.**

## 문제 & 해결

**막혔던 부분**: 처음엔 이 크래시를 워커 코드 안의 버그로 착각하고 `try/catch`를 여기저기 추가해봤다. 하지만 아무리 감싸도 크래시가 사라지지 않았다. 스택 트레이스를 자세히 보고 나서야 이 예외가 워커의 코루틴 실행 흐름과 무관하게, **시스템이 서비스를 실제로 기동하려는 시도 자체**에서 발생한다는 걸 알았다.

**해결**: "이 특정 방법(`setForeground()`를 무조건 호출)이 안전하지 않다"와 "포그라운드 승격이 필요하다는 문제 인식 자체가 틀렸다"를 구분했다. 되돌린 건 전자일 뿐, 후자는 여전히 유효한 문제로 남겨뒀다. 위험 대비 얻는 것이 크지 않다고 판단해서 당장은 손대지 않기로 했지만, 나중에 다시 시도한다면 `setExpedited(OutOfQuotaPolicy.RUN_AS_NON_EXPEDITED_WORK_REQUEST)`와 `getForegroundInfo()` 오버라이드를 쓰는 "expedited work" 경로로 가야 한다는 것도 같이 기록해뒀다 — Android가 expedited 작업에는 앱이 백그라운드에 있어도 포그라운드 승격을 예외적으로 허용하기 때문이다.

## 배운 점

- 안드로이드 버전이 올라가며 추가된 백그라운드 실행 제약은 "이 코드가 원래 하려던 일"과 "이 코드를 실행해도 되는 조건"을 분리해서 생각하게 만든다. 코드가 논리적으로 맞아도, 그걸 실행해도 되는 시스템 상태인지는 별개의 문제다.
- `try/catch`로 못 잡히는 예외가 있다면, 그 예외가 정말 내 코루틴/스레드 안에서 발생하는지부터 의심해야 한다. 이번 경우처럼 OS가 별도 컨텍스트에서 서비스를 기동하려다 던지는 예외는 애플리케이션 코드의 예외 처리 범위 바깥에 있을 수 있다.
- 고치려던 시도가 오히려 더 나쁜 결과(크래시)를 낳았다면, 주저 없이 되돌리는 게 맞다. 다만 되돌릴 때 "이 방법이 틀렸다"는 것과 "이 문제를 무시해도 된다"는 것을 같이 결론 내리지 않도록, 왜 되돌렸는지와 다음에 시도할 더 안전한 방법을 함께 기록해두는 게 중요하다.
