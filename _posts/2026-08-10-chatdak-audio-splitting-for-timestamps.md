## 오늘 한 일

- 문단마다 정확한 시작 시각을 붙이려 했는데, 쓰려던 STT 모델이 타임스탬프를 지원하지 않는다는 걸 확인
- 타임스탬프를 지원하는 다른 모델은 한국어 정확도가 낮다는 트레이드오프 확인
- 오디오 자체를 우리가 짧게 잘라서 STT에 넣는 방식으로 문제를 우회

## 핵심 작업 해설

### 문제: 정확도 좋은 모델은 타임스탬프가 없다

녹음을 문단 단위로 정리하면서, 문단을 탭하면 그 시점부터 바로 재생되게 하고 싶었다. 그러려면 문단마다 "몇 초에 시작하는 발화인가"를 알아야 한다.

가장 정확도가 좋았던 STT 모델(`gpt-4o-transcribe`)에 `verbose_json` 응답 형식(세그먼트별 타임스탬프를 포함)을 요청했더니 400 에러가 돌아왔다. **이 모델은 타임스탬프 자체를 지원하지 않는다.** 타임스탬프를 주는 다른 모델(`whisper-1`)은 있었지만, 한국어 정확도가 이 모델보다 떨어졌다. 정확도를 낮추는 건 이 프로젝트의 원칙("비용보다 정확도")과 정면으로 어긋났다.

### 해결: 모델에게 못 받으면, 우리가 직접 만든다

발상을 바꿨다. 모델이 타임스탬프를 안 주면, **오디오를 우리가 미리 알고 있는 시각 단위로 잘라서 보내면 된다.** 각 조각이 몇 초 지점부터 시작하는지는 우리가 자르는 시점에 이미 알고 있으니, 모델이 뭘 리턴하든 그 조각의 시작 시각은 항상 정확하다.

```kotlin
object AudioSplitter {
    private const val PIECE_SECONDS = 35

    fun split(audio: File, cacheDir: File): List<Piece> {
        val extractor = MediaExtractor().apply { setDataSource(audio.path) }
        // 오디오 트랙을 찾아 35초 단위로 MediaMuxer 로 무손실 재인코딩 없이 잘라낸다
        // 조각의 시작 시각(startMs)은 자르는 이 시점에 이미 알고 있는 값이다
        // ...
    }
}
```

`MediaExtractor`/`MediaMuxer`로 m4a를 35초씩 무손실 분할한 뒤, 조각 4개를 동시에 STT에 보낸다. 응답이 오면 미리 알고 있던 시작 시각을 그대로 붙여서 타임라인을 만든다.

```
[00:00] 첫 번째 조각의 전사 결과
[00:35] 두 번째 조각의 전사 결과
...
```

35초라는 조각 크기 자체가 기계적으로 자른 경계라서, 조각을 그대로 문단으로 쓰면 문장 중간에서 끊긴 것처럼 부자연스럽게 보이는 부작용이 있었다. 이건 별도로 조각들을 문장 경계 기준으로 다시 묶는 후처리(`Paragraphs.merge`)를 추가해서 풀었다 — 이때도 글자마다 원래 어느 조각에서 왔는지 기억해두기 때문에, 다시 묶은 문단의 시작 시각은 여전히 추정이 아니라 실측값이다.

### 덤으로 딸려온 이득

의도한 건 아니었지만, 오디오를 잘게 쪼개다 보니 파일 하나의 크기가 작아져서 API의 파일 크기 제한(25MB)에 걸리는 일이 사실상 없어졌다. 30분짜리 녹음도 조각 하나하나는 몇백 KB 수준이라, 원래 이 제한 때문에 별도로 필요했을 인코딩 재조정 작업을 하지 않아도 됐다.

**실측**: 26분 30초 녹음이 이 방식으로 46개 문단으로 정리됐고, 시작 시각은 `00:00`부터 `25:40`까지 전부 실제 발화 지점과 어긋남 없이 붙었다.

## 문제 & 해결

**막혔던 부분**: 처음엔 "STT 모델을 바꾸면 되지 않을까"로 접근했다. 타임스탬프가 있는 모델로 바꾸는 게 제일 간단해 보였기 때문이다. 하지만 실측 비교에서 한국어 인식 정확도 차이가 뚜렷하게 나서, 타임스탬프 하나를 얻으려고 전체 노트 품질을 떨어뜨리는 트레이드오프를 받아들일 수 없었다.

**해결**: "모델에게 기능을 요구하는 대신, 우리가 이미 알고 있는 정보(자르는 시점의 시각)를 활용하면 모델이 그 기능을 지원할 필요가 아예 없어진다"는 방향으로 문제를 재정의했다. 모델의 한계를 우회하는 게 아니라, 애초에 모델에게 그 책임을 맡기지 않는 구조로 바꾼 것이다.

## 배운 점

- 원하는 기능이 없다고 해서 항상 다른 도구로 바꾸는 게 답은 아니다. "이 정보를 내가 이미 갖고 있지 않은가"를 먼저 물어보는 게 더 나은 답을 줄 때가 있다.
- 하나의 제약(타임스탬프 없음)을 풀려고 한 결정이 다른 제약(파일 크기 제한)까지 같이 풀어주는 경우가 있다 — 처음부터 노린 게 아니어도, 문제를 구조적으로 다시 짜면 부수 효과가 따라온다.
- 정확도와 편의성 사이에서 트레이드오프를 저울질할 때는, "더 쉬운 길로 가면 무엇을 실제로 잃는가"를 실측으로 확인하고 결정하는 게 중요하다. 감으로 판단했으면 정확도가 낮은 모델을 그냥 썼을 수도 있다.
