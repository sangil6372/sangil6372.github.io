## 오늘 한 일

- "위젯 녹음 → 취소 → 앱 접속 → AI 요약 → 녹음본 삭제됨" 이라는 실사용 데이터 유실 신고 분석
- 취소 기능이 있는데도 왜 실패했는지 상태 저장 위치를 추적
- 취소 대상을 3단계로 찾는 방식과, 삭제 대신 이동으로만 처리하는 원칙으로 재설계

## 핵심 작업 해설

### 문제: 안전장치가 있는데도 파일이 사라졌다

이 앱은 녹음 취소를 눌러도 파일을 바로 지우지 않는다. `discarded/` 라는 별도 폴더로 옮겨서, 실수로 취소해도 나중에 복구할 수 있게 해뒀다. 그런데 실사용 중 이런 신고가 들어왔다.

> 위젯으로 녹음 → 취소 버튼 클릭 → 앱 켜서 확인 → AI가 알아서 요약까지 함 → 결과적으로 원본 녹음 파일이 사라짐

안전장치(휴지통 폴더)가 있는데도 파일이 날아갔다는 건, **취소 자체가 아무 일도 하지 않았다**는 뜻이었다.

### 원인: 필드 하나가 두 가지 생명주기를 동시에 갖고 있었다

녹음은 포그라운드 서비스(`RecorderService`)가 담당한다. 서비스 코드를 보니 지금 녹음 중인 파일 경로가 이렇게 저장돼 있었다.

```kotlin
class RecorderService : Service() {
    private var outputFile: File? = null   // 서비스 "인스턴스" 필드

    fun stopRecording() {
        // ... 저장 처리 ...
        stopSelf()
    }

    override fun onDestroy() {
        RecorderState.reset()   // 프로세스 전역 상태 초기화
        super.onDestroy()
    }
}
```

`outputFile`은 **이 서비스 인스턴스**가 살아있는 동안만 유효한 필드다. 반면 위젯이 화면에 보여주는 녹음 상태(`RecorderState`)는 **프로세스 전역** 싱글턴이다. 저장이 끝나면 `stopRecording()`이 `stopSelf()`로 서비스를 종료하고, `onDestroy()`가 `RecorderState`까지 초기화한다.

문제는 타이밍이었다. 저장 처리가 끝나고 서비스가 막 종료되려는 그 짧은 틈에 위젯의 취소 버튼을 누르면, 안드로이드는 **완전히 새로운 서비스 인스턴스**를 띄워 취소 요청을 전달한다. 이 새 인스턴스는 당연히 `outputFile`이 `null`이다 — 방금 저장된 파일에 대해 아무것도 모르는 "빈손" 상태로 취소 로직을 실행하니, `file != null` 조건에서 걸러지고 아무 일도 안 일어난 채 끝난다.

녹음 파일은 정리 대기 폴더에 그대로 남아있고, 예약된 AI 요약 작업도 살아있으니 앱을 켜면 그대로 요약까지 끝나버린다. 사용자 입장에선 "취소했는데 왜 요약이 됐지" + "결과적으로 취소함에도 없고 정리 대기에도 없으니 파일이 사라진 것"처럼 보였다.

### 해결: 취소 대상을 3단계로 폴백해서 찾는다

핵심은 취소 시점에 **어떤 서비스 인스턴스가 응답하든 상관없이** 취소해야 할 파일을 찾아낼 수 있게 하는 것이다. 인스턴스 필드 하나에만 의존하지 않고, 폴백 체인을 만들었다.

```kotlin
fun cancelTarget(): File? {
    // 1순위: 지금 이 인스턴스가 알고 있는 파일
    outputFile?.let { return it }
    // 2순위: 프로세스 전역 상태가 기억하는 현재 파일명
    RecorderState.fileName?.let { return File(recordingsDir, it) }
    // 3순위: 방금 전까지 녹음하던 파일명 (IDLE로 돌아가도 지우지 않는다)
    RecorderState.lastFileName?.let { return File(recordingsDir, it) }
}
```

`lastFileName`이 핵심이다. 이 값은 상태가 IDLE로 돌아가도 지우지 않고 남겨둔다 — "방금까지 뭘 녹음하고 있었는지"에 대한 유일한 단서이기 때문이다. 다만 아무 파일이나 취소 대상이 되면 위험하니, 그 파일이 아직 `pending/`(정리 대기) 폴더에 남아있는지는 반드시 다시 확인한다. 이미 처리가 끝난 파일은 이 체크에서 자연스럽게 걸러진다.

그리고 취소 경로 자체의 원칙도 다시 세웠다:

- **취소 경로에서는 `delete()`를 호출하지 않는다.** 옮기지 못했으면 그냥 그대로 둔다. 못 옮겼다고 지워버리면 "되돌릴 수 있게 한다"는 취소의 목적 자체를 어기게 된다.
- **상태를 비우는 건 파일을 옮긴 다음이다.** 순서가 바뀌면 "정리 대기 목록"이 제외 근거를 잃어버려서, 그 틈에 파일이 다시 정리 대기 화면에 새어 나올 수 있다.
- **취소하면 예약된 백그라운드 작업(WorkManager)도 반드시 같이 취소한다.** 파일만 옮기고 예약된 작업을 안 지우면, 이동한 파일을 대상으로 작업이 다시 돌 수 있다.

## 문제 & 해결

**막혔던 부분**: 처음 재현을 시도했을 때 두 번 연속 "재현됐다"고 잘못 판단했다. 파일이 여전히 정리 대기 폴더에 남아있길래 버그가 그대로라고 생각했는데, 실제 원인은 코드가 아니라 **화면이 잠긴 채로 테스트 입력을 보낸 것**이었다. 잠금 화면에서는 탭 이벤트가 앱에 전달되지 않는다.

**해결**: 입력을 보내기 전에 매번 잠금 상태를 먼저 확인하는 습관을 들이고 나서야 재현과 수정 확인을 제대로 구분할 수 있었다. 버그를 고쳤다고 믿었던 게 사실은 테스트 자체가 틀렸던 경우라, 검증 환경을 의심하는 것도 디버깅의 일부라는 걸 다시 배웠다.

## 배운 점

- **인스턴스 필드로 "지금 무엇을 하고 있는가"를 표현하면, 그 인스턴스가 죽고 새로 뜨는 순간 정보가 증발한다.** 안드로이드 서비스는 시스템이 언제든 인스턴스를 새로 만들 수 있으므로, 정말 중요한 상태는 인스턴스 생명주기 바깥(전역 싱글턴, 영속 저장소)에 둬야 한다.
- **안전장치(휴지통)가 있다고 안심하면 안 된다.** 안전장치로 가는 경로 자체가 실행되지 않으면 안전장치는 아무 의미가 없다. "지우지 않는다"보다 먼저 확인해야 할 건 "취소 로직이 정말 실행되긴 하는가"였다.
- 실기기 재현 실험에서 예상과 다른 결과가 나오면, 코드를 의심하기 전에 테스트 절차 자체(이번엔 잠금 화면)를 먼저 의심하는 것도 필요하다.
