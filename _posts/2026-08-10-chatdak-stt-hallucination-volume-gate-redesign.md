## 오늘 한 일

- 조용하게 녹음된 파일에서 STT가 실제로 말하지 않은 내용을 만들어내는 현상을 실측으로 확인
- 증폭·노이즈 제거 등 후처리로 고칠 수 있는 문제인지 다섯 가지 방법으로 비교 실험
- "크기"가 아니라 "말소리가 차지하는 시간 비율"로 판정 기준을 바꿔 음량 경고 기능을 재설계

## 핵심 작업 해설

### 문제: 볼륨을 키워도 STT가 없는 말을 만들어낸다

작게 녹음된 34.5초짜리 파일을 STT에 넣었더니 이런 결과가 나왔다.

> "지금 저희 개발자가 와서 담당하는 분이 있어요."

그런데 이 파일을 다섯 가지 방식으로 다르게 처리해서 다시 돌려보니 결과가 전부 달랐다.

| 처리 | 결과 |
|---|---|
| 원본 (평균 −40.5dB) | "개발자분이 나중에 주기적으로 업데이트를 해주시나요?" |
| 고역통과 필터 | "나중에 주기적으로 업데이트를 해주시나요?" |
| 노이즈 제거 | "**모델이 생성되면** 주기적으로 업데이트를 해주시나요?" |
| 필터+노이즈제거+압축 조합 | "**담당하는 분이 있습니다.**" |
| 동적 범위 압축 | "나중에 **출시되더라도** 주기적으로 업데이트를 해주시나요?" |
| (같은 원본을 다시 실행) | "지금 저희 개발자가 와서 담당하는 분이 있어요." |

**뜻이 완전히 다르다.** 이건 전사(transcription)가 아니라 모델이 지어내고 있다는 신호다. 게다가 같은 원본 파일을 그대로 재실행했는데도 세 번째로 다른 문장이 나왔다 — STT 모델 자체가 완전히 결정적이지 않다는 뜻이다.

### 증폭이 안 통하는 이유

"그럼 소리를 키우면 되지 않나?"가 자연스러운 다음 질문이었다. 27dB를 증폭해봤다.

- 원본(−40.5dB): 26자 분량 전사
- +27dB 증폭(−13.6dB): 33자 분량 전사

**글자 수가 거의 늘지 않았다.** 볼륨을 올리는 건 목소리와 배경 잡음을 똑같은 비율로 키우는 것이라 신호 대 잡음비(SNR)는 그대로다. 노이즈 제거나 압축도 원본에 없던 정보를 새로 만들어낼 수는 없다. 34.5초 중 실제 발화는 한두 문장뿐이었고, **못 담긴 소리는 후처리로 절대 복구되지 않는다.** 그래서 후처리 파이프라인을 만드는 대신, 녹음하는 순간에 사용자에게 알려주는 쪽으로 방향을 잡았다.

### 첫 시도 실패: "크기"로는 못 가른다

처음에는 녹음 중 측정한 최대 진폭이 특정 값 미만이면 경고를 띄우려고 했다. 그런데 조용한 방의 배경 잡음과 실패한 녹음의 피크 값을 실측해보니 겹치는 구간이 너무 넓었다.

| | 평균 음량 | 최대 음량 |
|---|---|---|
| 조용한 방 배경 잡음 (피크 기준) | level 24~43 | |
| 전사 성공한 녹음 | −32.4dB | −1.0dB |
| 지어내기가 발생한 녹음 | −40.5dB | −11.2dB |

평균 차이가 8dB밖에 안 나고, 배경 잡음의 피크가 그 사이에 끼어 있다. **크기만으로는 "말이 없는 녹음"과 "조용한 방에서 녹음한 정상적인 대화"를 구분할 수 없었다.**

### 해결: "말소리 비율"로 바꾼다

실제로 다른 건 크기가 아니라 **말소리가 차지하는 시간 비율**이었다. 성공한 녹음은 녹음 시간 내내 발화가 있었고, 문제가 된 녹음은 34.5초 중 실제 발화 구간이 2초 남짓(약 6%)이었다.

```kotlin
// level >= 55 를 "말소리"로 센다
// (배경 잡음 피크는 30 안팎, 실제 발화 피크는 78~98 사이)
val isSpeaking = level >= SPEECH_THRESHOLD

// 12초 넘게 녹음한 뒤, 말소리 비율이 15% 미만이면 경고
if (elapsedSec > MIN_SAMPLE_SEC && speechRatio < WARNING_RATIO) {
    notifyLowSpeechRatio()
}
```

12초라는 최소 기준을 둔 이유는, 말을 시작하기 전에 녹음을 먼저 켜는 게 보통이기 때문이다. 더 짧게 잡으면 정상적인 녹음에서도 항상 경고가 뜬다. 그리고 문구도 "소리가 작습니다"가 아니라 **"말소리가 거의 안 잡힙니다"**로 바꿨다 — 판정 기준이 크기가 아니라 발화 비율이라는 걸 문구에도 반영한 것이다.

경고는 앱 화면뿐 아니라 알림·위젯에도 띄웠다. 실제 사용 패턴이 위젯이나 잠금화면 타일로 켜고 화면을 안 보는 경우가 많아서, 앱 화면에만 두면 아무도 못 보기 때문이다. 대신 값이 실제로 바뀔 때만 알림을 갱신하도록 했다 — 100ms 주기로 계속 `notify()`를 부르면 시스템이 알림을 계속 다시 그려서 배터리도 쓰고 목록도 깜빡인다.

## 문제 & 해결

**막혔던 부분**: 임계값을 처음 잡을 때 근거가 서로 다른 두 수치를 비교하는 실수를 했다. 문서에는 "녹음 중 측정한 최대 진폭"으로 임계값을 잡았다고 적혀 있었는데, 그 임계값 자체는 외부 도구(ffmpeg)의 **평균(mean)** 음량에서 유도된 것이었다. 정작 코드가 실제로 재는 값은 **피크를 평활화한 값**이었다 — 비교 대상이 아예 달랐던 것이다. 그래서 처음 만든 게이트는 한 번도 작동하지 않았다.

**해결**: 두 값을 같은 기준으로 다시 실측하고 나서야 임계값을 제대로 잡을 수 있었다. "문서에 적힌 근거"를 그대로 믿지 않고, 실제로 코드가 재는 값이 무엇인지부터 다시 확인한 게 핵심이었다.

## 배운 점

- 모델이 확신에 찬 어조로 뭔가를 말한다고 해서 그게 실제로 들린 내용이라는 보장은 없다. 입력 정보가 부족하면 모델은 그럴듯한 문장으로 빈칸을 채운다.
- 후처리(증폭·노이즈 제거)는 있는 정보를 더 선명하게 만들 뿐, 애초에 담기지 않은 정보를 만들어낼 수 없다. 문제의 근본 원인이 "정보 부족"이라면, 문제를 해결할 수 있는 유일한 시점은 정보가 만들어지는 그 순간(녹음 시점)뿐이다.
- 두 값을 비교해서 임계값을 정할 때는 "같은 정의로 잰 값인가"를 반드시 확인해야 한다. 이름이 비슷해 보여도(평균 vs 피크) 실제로는 완전히 다른 값일 수 있다.
- 크기 기반 판정이 실패하면, "무엇이 진짜 다른가"를 다시 관찰해서 판정 기준 자체를 바꾸는 것도 방법이다. 이번엔 그게 크기가 아니라 비율이었다.
